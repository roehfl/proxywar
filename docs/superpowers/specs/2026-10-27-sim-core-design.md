# proxywar 시뮬레이션 코어·빠른 턴 모드 설계 (첫 기술 설계)

- 날짜: 2026-10-27
- 상태: 승인(2026-10-27)
- 전제: `docs/design/brainstorm-log.md`의 확정 결정과 게임 규칙 설계서(`2026-10-27-game-rules-design.md`). 이 문서의 결정도 같은 기록에 옮겨 두었다.
- 범위: 서버·계정·클라이언트 없이 로컬에서 도는 시뮬레이션 코어와 빠른 턴 모드. 게임 규칙 설계서 8절의 가설 A~E를 측정할 도구를 만드는 데까지다.

## 0. 한 문단 요약

매치 규칙 전체를 순수 TypeScript 코어(`packages/core`)로 만들고, 그 위에 빠른 턴 모드 도구(`packages/sim`)를 얹는다. 게임 상태는 직렬화 가능한 순수 데이터이고, 턴 처리는 `processTurn(상태, 확정 명령, 난수) → 새 상태 + 이벤트` 순수 함수이며, 참모는 `plan(보고서) → 계획` 비동기 인터페이스다. LLM 참모는 개발자 본인 구독의 `claude -p` 헤드리스로 부르고, 호출부는 교체 가능하다. 실행 설정에서 자리마다 규칙 참모·LLM 참모를 고르고 매치 턴 수를 정해 호출량을 조절한다. 매치마다 JSON 기록과 Markdown 보고서를, 배치마다 가설별 요약 표를 남긴다. 시드와 LLM 원문 기록으로 매치를 그대로 재현한다.

## 1. 하위 프로젝트 분해

기술 설계는 하위 프로젝트별로 설계 → 계획 → 구현을 따로 돈다. 이 문서는 1번이다.

| # | 하위 프로젝트 | 내용 | 상태 |
|---|---|---|---|
| 1 | 시뮬레이션 코어 + 빠른 턴 모드 | 매치 규칙, 규칙·LLM 참모, 봇, 매치 기록, 가설 측정 | 이 문서 |
| 2 | 서버 | 월드 서버, 실시간 1시간 턴 스케줄, 매치 관리, 저장 | 미설계 |
| 3 | 계정·연동 | 구독·API 키 연결과 보관 보안 | 미설계 |
| 4 | 클라이언트 | PC·모바일 등 다중 플랫폼 | 미설계 |
| 5 | 메타 | 명부·등급·유대·훈련·승급 | 미설계 |

2~5의 순서는 1의 측정 결과를 보고 정한다.

### 이 문서에 넣는 게임 규칙
매치 규칙 전부: 맵·자원·건물·군사·시야, 세팅 5종, 참모 메모, 조건부 명령, 출력 검증, 명령 확정 순서, 외교 6종, 영웅 능력치·특성·매치 안 성장·아웃라이어·부상·포로, 승리·탈락·점수.

### 넣지 않는 것
- 사람 조작: 명령 직접 수정, 수동 재계획, 탐험. 빠른 턴 모드는 봇만 돌리므로 쓰이지 않는다. 확정 순서의 "직접 수정" 칸은 타입만 두고 비워 둔다.
- 매치 밖 메타: 명부·유대·훈련·승급. 출전 영웅의 등급과 숨은 성장 계수는 실행 설정에서 직접 준다.
- 화면. 결과는 파일로 본다(5절).
- Claude 외 LLM 어댑터(OpenAI·API 키·로컬 모델). 인터페이스만 교체 가능하게 둔다.

## 2. 모듈 구성

`D:/game/proxywar/`에 npm workspaces로 두 패키지를 둔다. 언어는 TypeScript(Node 24). 나중에 서버는 `packages/server`, 클라이언트는 `apps/client`로 같은 저장소에 더한다.

### `packages/core` — 순수 TypeScript, Node API 금지
서버와 클라이언트가 그대로 import하는 부분이다.

| 모듈 | 하는 일 |
|---|---|
| `state` | 게임 상태 타입. 맵 데이터 + 실행 설정 → 초기 상태(`initState`) |
| `rules` | `processTurn`: 이동 → 조건 판정·반응 → 전투 → 생산·성장 → 외교 정산 → 승리·탈락 판정. 새 상태와 이벤트 목록을 돌려준다 |
| `orders` | 명령 타입, 항목별 검증, 확정 순서(직접 수정 > 제약 > 참모 계획) |
| `view` | 자리별 시야(안개) 계산과 보고서 데이터 |
| `prompt` | 프롬프트 조립, 길이 예산 자르기, 출력 스키마, 출력 파서. 템플릿은 게임 규칙이라 core에 둔다 |
| `staff` | 참모 인터페이스 `plan(입력) → Promise<계획>`와 규칙 참모 |
| `rng` | 시드 난수. 모든 무작위 폭은 여기서만 나온다 |
| `data` | 수치 표, 맵, 세팅 프리셋(JSON) |

### `packages/sim` — Node 전용
| 모듈 | 하는 일 |
|---|---|
| `llm` | `LlmClient` 인터페이스와 구현 셋(3절) |
| `llm-staff` | 프롬프트 조립 → `LlmClient` → 파서. 실패하면 계획 전체를, 잘못된 항목은 그 항목만 규칙 참모로 바꾼다 |
| `runner` | 매치 실행기, CLI, 배치 실행 |
| `report` | 매치 기록, Markdown 보고서, 배치 요약 표 |

## 3. 한 매치의 데이터 흐름

**시작**: 실행 설정(4절) → `initState`.

**반복** (게임 규칙 설계서 1.1의 순서)
1. **참모 호출**: 자리마다 `view(state, 자리)`로 시야 안의 보고서 데이터를 만들고 `plan()`을 부른다. 여섯 자리는 서로 독립이라 동시 호출 상한 안에서 동시에 부른다. 첫 턴 처리 전에도 초기 상태로 한 번 부른다.
2. **검증**: 호출 실패나 형식이 통째로 깨진 출력은 그 자리의 계획 전체를 규칙 참모가 대신한다. 잘못된 항목은 그 항목만 바꾼다. 대체 내역은 기록한다.
3. **확정**: 제약(영웅별 상시 명령 + 안전장치)을 적용해 확정 명령을 만든다.
4. **처리**: `processTurn(state, 확정 명령, rng)` → 새 상태 + 이벤트 목록. 같은 단계 안에서는 모든 자리의 명령을 동시에 처리하고, 동률은 시드 순서로 정한다. 외교 제안은 외교 정산 때 전달되고, 받은 쪽은 다음 계획에서 응답하며, 응답이 없으면 다음 정각에 만료된다.
5. **종료 판정**: 조기 승리, 남은 자리 하나, 또는 정한 턴 수 도달이면 종료하고 점수로 순위를 매긴다. 아니면 1로.

**재현성**: `processTurn`과 규칙 참모의 무작위는 모두 `(매치 시드, 턴, 자리)`에서 나온다. 비결정적인 것은 LLM 응답뿐이고, 원문을 기록해 재생한다.

**매치 기록에 남기는 것**: 실행 설정, 초기 상태, 턴별로 자리마다 보고서·LLM 입출력 원문·토큰 사용량·지연·대체 내역·확정 명령, 이벤트 목록, 턴 끝 지표(거점 수·자원·병력·점수), 참모 메모, 전쟁 일지. 턴별 전체 상태 스냅샷은 저장하지 않고, 필요하면 재생으로 만든다.

## 4. LLM 호출부와 프롬프트

### 4.1 `LlmClient`
`complete({ system, user, schema, model }) → { ok, output?, raw, usage{input, output}, latencyMs, error? }`. 참모 쪽은 이 인터페이스만 안다.

| 구현 | 내용 |
|---|---|
| `claude -p` 어댑터 | `claude -p --output-format json --json-schema <출력 스키마> --system-prompt-file <파일> --tools "" --no-session-persistence --model <별칭>`, 보고서는 stdin. 결과의 `structured_output`·`usage`·`is_error`를 읽는다. `--bare`는 구독(OAuth) 인증을 읽지 않으므로 쓰지 않는다. 모델은 별칭(haiku·sonnet·opus)으로 고르고, 봇의 저가 모델 자리는 haiku로 대신한다 |
| 가짜 | 시드로 형식이 맞는 계획이나 일부러 깨진 출력을 낸다. 테스트와 LLM 없는 반복용 |
| 기록 재생 | 매치 기록에서 `(턴, 자리)`의 원문 응답을 돌려준다 |

확인(2026-10-27, Claude Code 2.1.291): `--json-schema`를 주면 `structured_output`에 스키마에 맞는 JSON이 오고 `usage`에 입출력 토큰이 온다. haiku 한 번 호출에 약 7초. stdin 입력과 `--system-prompt-file`이 작동한다. `--bare`의 인증 제한은 `claude --help` 문구로 확인했다. 미확인: 구독 한도의 실제 횟수, 한도 소진 때의 오류 문구.

### 4.2 프롬프트
- 언어는 영어다. 규칙 설명·보고서·참모 메모·전쟁 일지 모두 영어로 쓴다(월드 서버 전제, 모든 플레이어·모델에 같은 템플릿).
- 시스템 쪽: 고정 규칙 설명 + 출력 형식. 사용자 쪽: 그 턴의 보고서(필수 정보 + 켠 정보 구성 + 지난 메모).
- 출력 스키마는 게임 규칙 설계서 3.5의 형식(영웅별 임무, 거점별 건설·모집, 외교 제안·응답, 참모 메모, 전쟁 일지)을 zod로 정의하고, 같은 정의에서 JSON Schema를 뽑아 `--json-schema`에 넘긴다.
- **길이 예산 단위**: core의 결정적 근사 함수로 센다(영어 글자 수 비례). 같은 글은 모델과 관계없이 같은 칸이 된다. 실제 토큰 사용량은 기록만 해서 근사와 비교한다. 모델별 예산 계수는 실행 설정에서 준다.

### 4.3 실패와 측정 오염
- 게임 규칙대로 재시도하지 않는다. 타임아웃·`is_error`·형식 오류·프로세스 오류는 실패이고, 규칙 참모가 대신한다.
- 매치 요약에 자리별 실패율을 적고, 기준을 넘은 매치는 배치 요약에서 **무효**로 표시한다.
- LLM 자리 전부가 연속으로 실패하면(한도 소진 추정) 배치를 멈추고 그때까지의 기록을 저장한다.
- 타임아웃, 무효 기준, 동시 호출 상한의 시작값은 구현 계획에서 정하고 실측으로 조정한다.

## 5. 실행 설정·CLI·출력물·게임 데이터

### 5.1 실행 설정 (JSON)
- 맵, 매치 턴 수, 시드, 동시 호출 상한, 타임아웃, 모델별 예산 계수.
- 자리 6개: 참모 종류(`rule` / `llm` + 모델 별칭), 세팅(프리셋 이름 또는 값 직접 지정), 출전 영웅 5명(이름·등급·숨은 성장 계수·특성).
- **실험 파일**: 기본 설정 하나 + 변형 목록(자리 구성·프리셋·계수 등) + 변형별 매치 수·시드 범위.
- 호출량은 자리 구성과 매치 턴 수로 조절한다. 가설마다 필요한 구성이 다르다(E: LLM 1명 대 규칙 참모 5명, A: 같은 모델·다른 프리셋 여럿).

### 5.2 CLI (`packages/sim`)
| 명령 | 하는 일 |
|---|---|
| `run <설정>` | 매치 하나 |
| `batch <실험>` | 변형 × 매치 수를 차례로 실행 |
| `replay <기록>` | 기록 재생 `LlmClient`로 다시 돌려 결과 일치 확인 |
| `report <기록>` | 보고서만 다시 만든다 |

### 5.3 출력물
`runs/<시각>-<이름>/` 아래에 두고 git에 넣지 않는다.
- `match.json`: 3절의 매치 기록.
- `report.md`: 최종 순위, 턴별 요약 표(자리별 거점·자원·병력·점수), 주요 이벤트(전투·함락·외교·약속 파기), 자리별 전쟁 일지와 참모 메모 전문, 대체·실패 통계.
- `summary.md`(배치): A 프리셋별 평균 순위, B 모델 × 계수별 승률, D 출전 영웅 평균 별 수와 순위의 상관, E LLM 참모 대 규칙 참모 승률, 무효 매치 수. C는 사용자가 `report.md`를 읽고 판정한다.

### 5.4 게임 데이터 (core `data`)
- **수치 표**: 전투·생산·유지비·건물·경험치 곡선·등급별 상승폭·점수 공식 계수를 한 파일에 모은다. 시작값은 구현 계획에서 제안하고 사용자 검토 뒤 실측으로 조정한다.
- **맵**: 손으로 만든 6인용 맵 1장(거점 30개 안팎)으로 시작한다. 측정이 돌아간 뒤 늘린다.
- **세팅 프리셋**: 봇 성격(공격형·내정형·외교형 등)을 세팅값 묶음으로 둔다. 구체 값은 구현 계획에서 제안한다.

### 5.5 규칙 참모
같은 세팅값을 읽는 결정적 휴리스틱이다. 성향 1~5는 행동 후보의 점수 가중치로, 지침은 해당 규칙의 켜짐·꺼짐으로 쓴다. 가설 E의 기준선이므로 일부러 약하게 만들지 않고, 세팅대로 판단하는 평범한 플레이어 수준을 목표로 한다.

## 6. 도구·오류 처리·테스트

### 6.1 의존성 (승인 2026-10-27, 버전은 같은 날 `npm view`로 조회)
| 패키지 | 버전 | 쓰는 곳 |
|---|---|---|
| `typescript` | 7.0.2 | 전체 |
| `zod` | 4.6.7 | core. 스키마 한 벌에서 TS 타입·런타임 검증·JSON Schema(내장 변환)를 얻는다 |
| `vitest` | 5.0.5 | 테스트. Node 24 지원, peer `vite` 함께 설치 |
| `tsx` | 4.23.15 | sim CLI 실행 |
| `@types/node` | 설치 시점 최신 | sim |

설치는 구현 계획의 첫 단계에서 에이전트가 한다.

### 6.2 오류 처리
- 경계에서 막는다. 실행 설정은 zod로, 참모 계획은 항목별로 검증한다. 안쪽 규칙 코드는 상태가 유효하다고 본다.
- 규칙 위반 상태(음수 자원, 없는 거점 등)는 버그이므로 예외로 멈춘다.
- LLM 실패는 4.3대로 대체하고 기록한다.

### 6.3 테스트 (vitest)
- 단위: 턴 처리 단계별(이동·조건부 명령·전투·생산·외교 정산·승리 판정), 명령 검증·확정 순서(예: "수도 방어 전담"이 공격 임무를 막음, "수도 최소 수비 3"이 수도 병력을 남김), 시야, 프롬프트 조립·예산 자르기, 출력 파서(정상·항목 오류·통째로 깨짐).
- 결정성: 같은 시드·같은 명령 → 같은 결과.
- 통합: 규칙 참모 6명 120턴 완주, 가짜 LLM 참모가 섞인 매치, 기록 → 재생 일치.
- 실제 `claude -p` 호출은 자동 테스트에 넣지 않는다(구독 한도). 짧은 스모크 실행을 수동 검증 단계로 둔다.

## 7. 완료 기준

1. 규칙 참모 6명이 120턴 매치를 결정적으로 완주하고 `report.md`가 나온다.
2. `claude -p` LLM 참모가 낀 매치가 완주하고 실패·대체가 기록된다.
3. `batch`가 가설 A·B·D·E 요약 표를 만든다.
4. `replay`가 기록한 매치를 같은 결과로 재현한다.
5. 사용자가 LLM 매치의 `report.md`로 가설 C를 판정할 수 있다.

가설의 참·거짓 판정은 완료 기준이 아니다. 이 프로젝트는 판정 도구까지다.
